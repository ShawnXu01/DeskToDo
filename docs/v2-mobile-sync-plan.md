# V2 跨端协同（手机端）规划备忘录

> 本文档用于记录 V1 阶段讨论过、但决定推迟到 V2 实现的内容，避免后期重新踩坑。
> V1 范围：仅 PC 端，**飞书相关功能完全不做**，但预留同步接口供 V2 接入。

## V1 与 V2 的边界

- **V1 做的事**：本地 JSON 持久化 + GitHub Gist 云端同步（用作"多台 PC 之间的云盘式备份/同步"，不涉及手机）
- **V2 才做的事**：飞书 Bot 接收/回复消息，实现手机创建任务、查看本周任务

## V1 阶段需要预留的接口设计原则

- 同步逻辑应该抽象成一个"同步提供方（Sync Provider）"接口，V1 只实现 `GistSyncProvider` 一种
- 任务的创建来源（来自 PC 本地 / 来自外部同步）在数据模型里要能区分（比如记录 `source` 字段），方便 V2 加入飞书来源后，排查问题时知道任务是哪来的
- 冲突解决策略（时间戳覆盖 + 墓碑软删除）在 V1 就要做完整，因为这套机制 V2 加入飞书后会直接复用，不是 V2 才设计

## V2 启动前必须先验证/确认的问题（按风险排序）

1. **飞书接收消息的技术路径**：群聊 Webhook 机器人只能发不能收，必须用"自建应用 + 事件订阅"才能接收用户消息。需要确认：
   - 你的飞书账号/团队能否申请自建应用并开通事件订阅权限
   - 飞书是否支持"长连接（无需公网地址）"接收事件，这是我们坚持"无服务器架构"的关键依赖，需要写一个最小 demo 脚本实测
2. **PC 离线时手机消息会不会丢失**：长连接依赖 PC 端程序在线才能实时收到事件，需要确认飞书断线重连后是否会补发错过的消息，否则需要做"离线消息提示用户重发"之类的兜底
3. **被动问答的指令格式设计**：手机发消息创建任务时的固定格式（如 `新建 任务名 日期`），需要考虑常见的相对日期表达（"周五" "下周一"）怎么解析，避免失败率过高打击使用体验
4. **创建任务的字段精简**：手机端入口大概率不会输入"周期规则"，V2 设计上手机创建的任务默认是"单次"类型即可，复杂编辑还是回到 PC 端

## 暂定但尚未实现的功能点

- 主动推送（如每天早八点推送当日任务到飞书）——V1讨论时提到过，明确推迟到 V2，且要单独评估是否需要
- 手机端查看范围目前定的是"本周"，没有讨论再往后的查询需求，留给 V2 看用户反馈再扩展
- **`TaskStore.load()` 对损坏/空 JSON 文件的容错处理**：2026-07-08 实测发现，如果 `tasks.json` 因异常关机等原因被写坏（如被清零成非法 JSON），当前 `deskcal/core/storage.py` 里 `TaskStore.load()` 会直接抛 `JSONDecodeError` 导致整个程序无法启动。计划在 V2 里改成：加载失败时自动把坏文件备份为 `.bak` 并以空任务列表启动，而不是让程序完全打不开。V1 阶段本次先手动处理（备份坏文件 + 重置为空 JSON），未改代码。

## 2026-07-08 更新：远程修改的三条技术路线对比（飞书 Bot / 微信小程序 / H5 网页）

前提：V1 已经把 GitHub Gist 变成了"数据总线"——任何一端只要能读写那个 Gist
（拉取 → 按 `updated_at` 时间戳合并 → 推回），PC 端最迟 5 分钟后就会自动收到改动。
所以"远程修改"的本质问题只有一个：**手机上的操作怎么写进 Gist**。三条路线只是这一步的不同实现。

### 路线 A：飞书自建应用 Bot（长连接，PC 端处理）

- 架构：手机发飞书消息 → 飞书事件订阅（长连接 SDK）→ **常驻 PC 上的 DeskToDo 进程**解析指令 → 直接改本地 TaskStore（下轮同步自动推到 Gist）
- 优点：零服务器、零费用；网络全程走国内（手机不需要访问 GitHub）；开发量最小（PC 端加一个 service + 指令解析器）
- 缺点：**PC 关机/睡眠时消息收不到**（长连接断开后飞书是否补发离线事件需要实测，V1 备忘录里已列为风险 2）；文本指令格式的解析失败率影响体验；查看任务只能靠 Bot 回消息，排版能力有限
- 适合场景：PC 基本常开、只需要"随手丢一条待办进去"

### 路线 B：微信小程序（推荐认真评估，但成本最高）

- 关键技术约束（决定架构，需要在动手前逐条核实）：
  1. 小程序 `wx.request` 只能访问**已备案域名**的白名单，`api.github.com` 不可能加入白名单 → **小程序无法直连 GitHub API**
  2. 绕开方式是**微信云开发（云函数）**：小程序调云函数不受 request 域名白名单限制，云函数在腾讯云侧出网访问 `api.github.com`，充当中转。云开发目前是付费的（基础套餐约 20 元/月量级，**具体价格需查证**）
  3. 个人主体可以注册小程序（免费），但每次发版要过微信审核；"工具类"一般好过审
- 架构：小程序 UI → 云函数（存 Gist Token，做 pull/merge/push）→ Gist → PC 端 5 分钟轮询接收
- 优点：体验最好（真正的表单 UI，新建/勾选/查看都不依赖文本指令）；**不依赖 PC 在线**；微信入口对家人朋友最友好
- 缺点：开发量最大（WXML/WXSS/JS 全新技术栈 + 云函数里要用 JS 重写一遍 merge 逻辑）；每月固定费用；审核流程；Token 存放在云环境配置里需要考虑安全
- 风险点：腾讯云函数出网访问 GitHub 的稳定性需要写个最小 demo 实测

### 路线 C：H5 网页（GitHub Pages 托管，最轻方案，可作为 V2 最先落地的验证方案）

- 架构：纯静态页面（托管在 GitHub Pages）→ 浏览器 JS 直接调 GitHub Gist API（Token 首次粘贴后存 localStorage）→ 手机浏览器"添加到主屏幕"当 App 用
- 优点：零服务器、零费用、无审核；开发量中等（一个单页应用，merge 逻辑用 JS 重写）；不依赖 PC 在线
- 致命短板：**国内手机网络直连 `api.github.com` 不稳定**（这是决定性因素，需要用自己的手机在移动网络下实测）；Token 明文存在手机浏览器里
- 适合场景：如果实测 GitHub API 在你常用网络下可达，这是性价比最高的方案

### 三路线对比总结

| 维度 | A 飞书 Bot | B 微信小程序 | C H5 网页 |
| --- | --- | --- | --- |
| 依赖 PC 在线 | **是**（硬伤） | 否 | 否 |
| 国内网络可靠性 | 好 | 好（云函数中转） | **差/需实测** |
| 开发量 | 小 | 大 | 中 |
| 固定成本 | 0 | ~20 元/月（需查证） | 0 |
| 交互体验 | 文本指令 | 最好 | 好 |
| 发布门槛 | 无 | 微信审核 | 无 |

### 建议的推进顺序

1. **先做两个半天级别的实测 demo，再定路线**：
   - 实测 1：手机（移动网络 + 家里 WiFi）浏览器里用 fetch 调 `api.github.com/gists`，看可达性 → 决定路线 C 是否成立
   - 实测 2：开通微信云开发，写一个云函数访问 GitHub API → 验证路线 B 的中转可行性和延迟
2. 无论选哪条，先在 PC 端把"同步间隔"做成可配置（远程改动后 5 分钟才上屏，体验上可能要缩短）
3. 手机端 V2 首版功能范围维持之前的结论：新建单次任务 + 勾选完成 + 查看本周；周期规则等复杂编辑仍回 PC
4. merge 逻辑如果要在 JS 端重写（路线 B/C），把 `deskcal/core/sync/__init__.py` 的 `merge_payloads` 语义原样翻译，并把现有 `tests/test_sync_merge.py` 的用例也翻译过去当回归测试
